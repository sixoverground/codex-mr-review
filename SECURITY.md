# Security

## Reporting a vulnerability

Please report security problems privately through GitHub's private vulnerability reporting on this repository (the "Report a vulnerability" button under the Security tab). Do not open a public issue. We aim to acknowledge a report within a week.

## What this tool handles

This tool holds a GitLab token with permission to comment on merge requests, and runs a model over code that the merge request's author controls. The rules it is built around:

- **The token never reaches the model.** Codex runs as a child process with an allowlisted environment (`src/env.js`), so the GitLab token, `CI_JOB_TOKEN` and the tool's own `CODEX_MR_REVIEW_TOKEN` are not in it. A test checks the environment the child actually receives.
- **The token is never logged or posted.** The values of `GITLAB_TOKEN`, `CI_JOB_TOKEN`, `CODEX_MR_REVIEW_TOKEN`, `OPENAI_API_KEY` and `CODEX_API_KEY` (when 8 characters or longer) are replaced with `[redacted]` in everything the tool writes: diagnostics, error messages that quote Codex, and findings and summaries in both output formats. All output passes through one redaction point (`src/redact.js`, applied to stdout and stderr at the top of `main`). The API keys do reach Codex, which needs them, so this is what stops Codex echoing one into the log.
- **The model cannot write the review marker.** The marker is added by the tool after Codex exits successfully, using a commit sha from the CI environment. Any marker-like text in model output is removed before posting.
- **The review checkout holds no credential.** Codex works in a temporary local clone of the head commit (`git clone --shared`), not a `git worktree`, because a worktree shares the CI checkout's config, where the runner leaves the job token in the remote URL. Before Codex starts, the clone's own config is stripped of userinfo in every remote URL, `http.*.extraheader`, every `credential.*` setting, `include` directives and credentialed `url.*.insteadOf` rewrites, and the tool fails the run if any is left. The CI checkout's config is not touched.
- **The diff cannot rewrite its own review instructions.** The review runs in that temporary checkout of the head commit in which every `AGENTS.md` and `AGENTS.override.md`, at any depth, is the base commit's copy, or absent when the base has none. That covers guidance files the head adds, edits or deletes. The summary says when the head changed any of them.
- **A guidance symlink in the base is resolved in the base, never recreated.** A base `AGENTS.md -> instructions.md` is followed inside the base commit's tree (chains and directory links included) and the base content is written as a regular file, so a change cannot rewrite its instructions by editing the target. A head change to any file or link such a symlink resolves through is reported as a change to `AGENTS.md`. A base link that leaves the repository, is missing or loops fails the run before Codex starts.
- **Symlinks in the change are never followed when resetting guidance.** An existing entry is unlinked without being followed before the base copy is written. If any directory on the way to a guidance path is a symlink, or the parent resolves outside the worktree, the run fails before Codex starts.
- **Nothing Codex starts outlives the review.** Codex runs in its own process group, and the whole group gets SIGKILL when Codex exits, on every path, before the worktree is removed.
- **The reviewer's own Codex config is not used.** Codex runs with `--ignore-user-config`, so MCP servers and model settings from `~/.codex/config.toml` do not apply to a review.

- **The marker is the tool's, not the model's.** It is built by the tool from the CI sha (or the checkout's), only after Codex exited successfully and every finding was posted, and it goes in a top-level note. A failed run posts no marker.
- **Everything from Codex is scrubbed at one point.** Every string in a review (path, title, body, explanation, and any field added later) is scrubbed of the marker prefix right after Codex returns, before anything is printed or posted, and printed text is scrubbed again on its way out. A finding whose path contains a newline, a control character or an angle bracket fails the run.
- **Redaction comes before any cut.** Everything Codex returns is redacted whole as soon as it is read, before parsing. Any text shortened for a message (a GitLab error, the failure note) is scrubbed and redacted whole first, then reshaped, then cut (`excerpt` in `src/redact.js`), so a cut can never leave part of a secret behind.
- **Nothing is posted before the review is validated.** The scrubbed review is checked against the output schema, and for a title or body that scrubbing emptied, for every output format and before any write to GitLab. A review that fails gets a failure note, no findings and no marker.
- **Redirects are never followed.** A 3xx from the GitLab API fails the request with its status and the target's origin only, so the token is never resent to another host.
- **Only the tool's own threads count for dedupe.** A finding is skipped or reopened only when its fingerprint is on a thread the token's own account started, so a fingerprint pasted by someone else cannot hide a finding. Model text cannot carry a fingerprint either: the prefix is scrubbed.
- **Post as a dedicated identity.** Anyone who can comment can type a marker by hand, so a consumer should accept a marker only from the account the tool posts as. Use a bot user or a project access token for `CODEX_MR_REVIEW_TOKEN`, not a person's token.

## What remains

These are not closed by the tool, and a project adopting it should accept them knowingly.

- **The read-only sandbox can read anything the runner's user can.** Codex's sandbox blocks writes and network access, but not reads. A merge request's author can ask the model, through the code under review, to read and quote other files on the machine: other checkouts, SSH keys, shell history, the runner's own config, the CI checkout's `.git/config` with its job token. **Run the runner as a dedicated user** that owns nothing else, especially a shell-executor runner on a personal Mac, and keep that user's home free of anything you would not publish.
- **What a finding quotes is visible to everyone on the project.** Findings are posted as merge request threads. The tool redacts the secrets it knows (its own token, `CI_JOB_TOKEN`, `GITLAB_TOKEN`, `OPENAI_API_KEY`, `CODEX_API_KEY`), but it cannot recognise any other secret the model quotes.
- **Global Codex guidance still applies.** Codex reads `AGENTS.md` or `AGENTS.override.md` from its home (`$CODEX_HOME`, default `~/.codex`) even with `--ignore-user-config`. Checked on codex-cli 0.147.0 on 2026-11-18: a one-line instruction in `~/.codex/AGENTS.md` showed up in the review. That file belongs to the runner's user, not to the merge request, so it cannot be used by an author to steer their own review, but it does change every review. The tool does not move Codex to an isolated home, because a ChatGPT login stores refreshable credentials there and a copy could fall out of step with the original; instead it warns when the file has content. Keep it empty for the runner user.
- **The user's global git config is not changed.** The review checkout's own config is cleaned, but a credential helper in the runner user's `~/.gitconfig` still exists. The sandbox blocks network access, so Codex cannot use it to fetch, but the dedicated-user advice above applies here too.
- **Usage and rate limits.** With a ChatGPT login, reviews draw on that account's Codex usage. A rate limit fails the review: the job goes red, posts a failure note and no marker.
- **A shared machine is shared.** A shell executor runs jobs as the runner user, alongside whoever else uses the machine. It isolates nothing beyond what that user's permissions do.
- **Protected variables.** A token stored as a protected CI/CD variable is not given to pipelines on unprotected branches. The job then fails saying the token is missing and posts nothing; it never passes silently.
